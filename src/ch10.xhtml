第 10 章 实战：从需求到交付的完整演练

用一个贴近本书写作环境的例子串起全书：给一个 Unity 手游客户端加"聊天撤回"功能。例子中的技术点来自真实项目的 CLAUDE.md 约定。

10.1 需求 → 委派指令

产品说"加个消息撤回"。直接转述给 AI 是反模式。先按四要素翻译成委派指令：

功能: 聊天系统加"撤回消息",发出后 2 分钟内可撤回。
约束:
- 遵守项目 CLAUDE.md 的 MVVM 三件套(InitVM/InitBinds/InitEvents)
- 不改 UI 布局文件,只改 Lua 逻辑层
验收:
- 发消息→撤回→对方不再显示,本地服务自测通过
- luacheck 无新增告警
执行方式:
- 非琐碎改动: 先 plan 后 execute
- review 走独立上下文的 code-reviewer

注意两点：约束里直接引用 CLAUDE.md 的已有约定(不用重新解释)；验收里写明复现路径。

10.2 plan 阶段

切换计划模式(或 /oh-my-claudecode:plan)。AI 探索代码库后给出方案：

  • 聊天 UI 在 UI/Chat/UIChatMain.lua,消息数据在 _G.Root.Chat,撤回需要客户端标记 + 服务器广播；
  • 方案：协议加撤回请求/广播 → Mediator 处理 → VM 标记消息状态 → UI 订阅变化刷新列表。

你审方案的三件事：目标对不对、边界清不清、验证方式是否可信。确认后进入执行。

10.3 execute 阶段

/oh-my-claudecode:execute。executor 按计划实现：

  1. 协议层：撤回请求 + 广播消息定义；
  2. Mediator：_G.MediatorChat:RecallMessage(msgId)，更新 _G.Root.Chat；
  3. UI 层：UIChatMain 订阅消息变更，撤回的条目渲染为提示文案。

每步要求验证证据。执行中发现协议字段和服务器对不上，AI 停下来报告而不是硬编——这正是 3.3 节"先想后做"约定的作用。

10.4 review + verify 阶段

code-reviewer 在独立上下文里审出两个问题：

  • 撤回计时器没用 self:StartTimer，普通 _G.Timer.Add 在 UI 关闭后不会自动清理 → major；
  • 本地化文案 _L("CHAT_RECALL") 没检查是否带格式参数 → minor。

executor 修复后复审通过。verifier 汇报验证证据：luacheck 零告警、自测录像/截图、边界用例(恰好在 2 分钟边缘撤回)。

你验收后提交：

git add -p   # 逐块检查,只提交本功能相关改动
git commit   # "聊天: 新增消息撤回功能"

10.5 交付后:沉淀

收尾不是提交完就完。按第 8 章标准做沉淀：

  • 过程中"配置表必须先改 Excel 再导出"说到了第二遍 → 写入项目记忆/CLAUDE.md；
  • 排障 35 分钟的"撤回广播与重连时序问题" → 写一页 wiki debugging 复盘;
  • "日报流程"已经手工走过三遍 → 下次用 skillify 固化。

10.6 复盘:本次指挥的得失

做得好因为
四要素指令 + 关卡确认方向错误为零,返工只有一次小修
review 走独立上下文抓到了作者自己看不见的清理类问题
要求验证证据没有依赖"AI 自称完成"
可以更好因为
验收里漏了"重连后撤回状态正确"用例边界用例在 review 阶段才补上
