速读版：全书浓缩成十条最佳实践

没时间读全书？照着下面十条做，就能拿到这本书八成的收益。每条末尾括号里是展开讲的章节，遇到问题再回去翻。

  1. 把它当"每天失忆的聪明同事"。它很聪明，但不记得你的项目和昨天说过的约定。要紧的事写进 CLAUDE.md 和记忆，不要每次口头重说。（第 1、4 章）
  2. 委派，不要问答。一条合格的指令 = 目标 + 约束 + 验收标准 + 执行方式。"帮我优化一下"是反模式。（第 3 章）
  3. 验收标准是自动化的地基。写成机器可判定："luacheck 通过、复现路径不再出错"，而不是"做好点"。验收越明确，AI 越能自己循环到达标，你越不用盯。（第 3、7 章）
  4. 非琐碎改动，先计划后动手。计划模式（Shift+Tab）或 OMC plan 出方案；你确认的是方向和边界，不是细节。计划未确认，不许写代码。（第 6 章）
  5. 减少打扰，从权限自动化开始。日常用 claude --permission-mode auto 起步，高频命令加白名单（.claude/settings.json 的 permissions.allow）；--dangerously-skip-permissions 只在容器或虚拟机里用。（第 2 章、附录 A.2）
  6. 作者不许自审，完成必须给证据。review 交给独立上下文的 code-reviewer；verify 要测试输出、构建日志，不信"我觉得完成了"。（第 5、6 章）
  7. 方向错了立刻 Esc。打断比返工便宜；双击 Esc 回退到走偏的那条消息，从那里重新指挥。（第 2 章）
  8. 边界清晰就放权。验收可自动化的任务交给 autopilot / ralph 无人值守；放行前保证 git 工作区干净，出问题整体回滚。自动化程度跟着回滚能力走。（第 7 章）
  9. 第二遍记忆、30 分钟复盘、第三遍技能化。解释到第二遍，写进记忆或 CLAUDE.md；排障超 30 分钟，wiki 复盘一页；同一流程走第三遍，skillify 固化成技能。（第 8、9 章）
  10. 上下文是唯一货币。给文件路径让它自己查，别贴几千行日志；新任务 /clear 开新会话，历史太长 /compact。（第 1、2 章）

日常工作流（一句话版）

说清目标+验收 → 确认计划 → 放手执行(auto 模式+白名单) → 看证据验收 → 值得记的沉淀下来

全书就是这十条的展开：第 1-4 章讲"指挥与记忆"，第 5-7 章讲"编排与自动化"，第 8-9 章讲"沉淀与进化"，第 10 章是一次完整演练。

前言：从“敲代码的助手”到“可指挥的团队”

如果你只是把 Claude Code 当成一个“会聊天的补全工具”，那它大概只发挥了 10% 的能力。真正的差距不在模型本身，而在你怎么指挥它：你给它的上下文有多准确、你定义的成功标准有多清晰、你有没有为它建立一套能沉淀经验、越用越聪明的机制。

这本小册子想回答三个问题：

  1. 怎么指挥 AI —— 怎么写需求、怎么给上下文、怎么定义“做完了”；
  2. 怎么让 AI 持续学习 —— 怎么让它记住你的偏好、你的项目、你踩过的坑，而不是每次对话都从零开始；
  3. 怎么让 AI 进化 —— 怎么把一次性的好经验固化成可复用的技能、工作流和知识库，形成“越用越强”的正循环。

为此我们会以 oh-my-claudecode（OMC）插件为主要工具。OMC 是 Claude Code 上的一个多智能体编排层：它把“规划、执行、审查、验证”拆成不同的专职 Agent，把“记忆、技能、知识库”做成可持久化的模块，天然适合搭建这套持续进化的体系。

第 1 章 心智模型：AI 是一个"新来的、很聪明但什么都没记住"的同事

指挥 AI 的所有技巧，都建立在一个准确的心智模型上。请把 Claude Code 想象成一位新来的高级工程师：

  • 他非常聪明，读过几乎所有的开源代码和文档，写代码、查问题都比大多数人快；
  • 但他对你的项目一无所知，不知道你们团队怎么命名、哪些文件碰不得、上周刚踩过什么坑；
  • 而且他每天早上都失忆——昨天你们配合得再好，今天他又是"新人"。

一旦接受这个模型，你就明白指挥 AI 的三大任务：

  1. 给对上下文：告诉他是谁、在哪、要干什么。这是"提示词"的本质。
  2. 建立记忆：把"他每次都要重新知道的东西"写进他会自动读到的文件里，而不是靠聊天里说一遍。
  3. 固化流程：把配合得好的一次性流程固化成技能和工作流，让他下次不用你重新教。

这三件事分别对应本书的三个主题：指挥、学习、进化。后面所有章节都是这三件事的具体展开。

1.1 指挥 ≠ 问答，而是"委派 + 验收"

新手用 AI 的方式是"问答式"：问一句、答一句，AI 每走一步都等你确认。这是最低效的用法。高效的做法是委派式：像给下属派活一样，说清目标、边界、验收标准，然后放手让它干，最后验收结果。

两种方式的差别，在任务变大后会被急剧放大。一个"帮我修这个 bug"的问答式对话可能来回十几轮；而一个委派式的指令可以是：

修复背包系统在断线重连后物品数量显示错误的 bug。
约束:
- 不要改 UI 布局相关代码
- 复现路径: 主界面 → 背包 → 断线重连
验收:
- 按上述路径复现不再出现错误数量
- luacheck 通过
先在计划模式给出修复方案，等我确认后再动手。

注意这段指令里的四个要素：目标、约束、验收标准、执行方式。第 3 章会专门展开怎么写这样的指令。

1.2 上下文是唯一货币

对 AI 来说，"它知道什么"几乎完全决定了"它能做多好"。它的上下文窗口是有限的，塞进去的每一条信息都在争夺空间。所以指挥 AI 的一半功夫在管理上下文：

  • 该给的要给：项目约定、领域知识、踩坑记录，要写进它每次都会读的文件（第 4 章）；
  • 不该给的别塞：几千行的日志、无关文件的内容，直接丢进对话只会稀释重点。要学会用搜索、摘要、文件路径代替原文粘贴。

1.3 单体 → 编排：为什么需要 OMC

当任务小的时候，一个 Claude Code 会话就够了。但当任务变成"重构一个模块"这种规模，单体会话的问题暴露出来：上下文越长越贵、越慢，而且"自己写自己查"容易既当运动员又当裁判。

OMC 的解法是分工：主会话负责理解你的意图、拆解任务、把控方向（当好"指挥官"），具体执行交给专职 Agent——规划找 planner、写代码找 executor、审查找 code-reviewer、验收找 verifier。这就像一个技术负责人不再亲自写每一行代码，而是带一个各司其职的团队。

记住这句话：你的角色升级了——从"程序员"升级为"技术负责人 + 教练"。你不再写每一行代码，而是：定目标、给上下文、验收结果、并且不断把好的经验沉淀下来教给团队。

第 2 章 Claude Code 快速上手

本章把后面会用到的 Claude Code 基础能力过一遍。已经熟练的读者可以直接跳到第 3 章。

2.1 安装与启动

npm install -g @anthropic-ai/claude-code   # 安装
claude                                     # 在项目根目录启动
claude -p "总结这个仓库的结构"               # 非交互模式(适合脚本调用)
claude --resume                            # 恢复上一次会话

2.2 会话即工作区

Claude Code 的基本单位是会话。你在一个终端里和它对话，它可以读写文件、执行命令、搜索代码。启动后它会自动读取以下上下文（按优先级）：

文件作用
~/.claude/CLAUDE.md全局个人指令，所有项目生效
项目根/CLAUDE.md项目指令，随代码入库，团队共享
项目根/AGENTS.md给子智能体/其他工具读的项目说明
.claude/settings.json权限、hooks 等行为配置

所以"每次都要重复说的话"，正确做法不是每次打一遍，而是写进上面这些文件。这是第 4 章记忆体系的入口。

2.3 交互基本功

  • 斜杠命令：输入框里 / 开头，如 /clear（清空上下文开新任务）、/compact（压缩历史省 token）、/model（切换模型档位）、/resume、/config；
  • 计划模式：Shift+Tab 切换到 Plan Mode，AI 只探索和出方案不动代码，适合任何非琐碎改动；
  • 打断与纠偏：随时 Esc 打断，说"不对，方向错了"比让它跑完再返工便宜得多；
  • Esc 退 Esc 进：连按两次 Esc 回退到历史某条消息，从那里重新指挥，而不是道歉后继续；
  • @文件引用：输入 @ 可以精确引用文件，把上下文指给它，而不是复制粘贴内容。

2.4 权限模型

Claude Code 的每个敏感操作（写文件、执行命令）都会请求许可，权限模式有：

  • 默认模式：每步询问，最安全也最累；
  • 自动接受编辑（acceptEdits）：文件编辑自动通过，命令仍询问——日常开发推荐；
  • 计划模式：只读不动手，出方案；
  • bypassPermissions：全放行，只在你完全信任的任务里用（比如让它自己跑测试循环）。

可以配置白名单减少询问频率（.claude/settings.json 的 permissions 段，或用 /fewer-permission-prompts 技能自动扫描并生成白名单）。原则：读操作大胆放行，写操作和破坏性命令保持确认。

2.5 Hooks：在关键节点安插你的规则

Hooks 是 Claude Code 的钩子机制：在工具调用前后、会话开始等时机自动执行你定义的动作，比如：提交前强制跑 lint、把输出重定向到摘要工具、注入提醒。配置在 settings.json 里。当你发现"我每次都要口头提醒 AI 某件事"时，就该考虑把它做成 hook——口头提醒会忘，钩子不会。

2.6 子智能体

复杂任务可以派生子智能体（subagent）：让一个独立上下文的 Claude 去搜代码、做研究、写方案，只把结论带回主会话。这样可以避免主会话被海量中间输出撑爆。OMC 本质上就是把这套机制产品化成一个完整的 agent 目录（第 5 章）。

第 3 章 指挥的艺术：需求、上下文与成功标准

同一件事，指挥得好十分钟后完成，指挥得不好反复返工一下午。本章给出一套可直接套用的"委派指令"写法。

3.1 委派指令四要素

一条好的委派指令 = 目标 + 约束 + 验收标准 + 执行方式。

要素回答的问题反例正例
目标做什么"优化一下背包""修复背包断线重连后数量显示错误"
约束不能做什么(无)"不改 UI 布局；不动 DataAccess 生成代码"
验收怎么算做完"做好点""复现路径不再出错；luacheck 通过"
执行方式过程怎么控制(无)"先计划模式出方案，确认后再改"

其中验收标准最容易被忽略、也最有杠杆。把"修好这个 bug"翻译成"先写一个能复现它的测试，然后让它通过"，AI 就能自己循环直到达标，不需要你每一步盯着。模糊的验收标准 = 你自己变成了验收标准，每一步都得你确认。

3.2 不同规模的任务，不同的指挥粒度

琐碎任务：一句话

把这个文件里的 var 全部改成 const

直接干，别过度规划。用判断力，别用流程。

中小任务：目标 + 验收

给聊天系统加"撤回消息"功能，2 分钟内的消息可以撤回。
- 参考 UIGoodsBuy 的 MVVM 写法(InitVM/InitBinds/InitEvents)
- 验收: 本地起服务自测通过 + luacheck 无报错
- 先列改动计划再动手

大任务：分阶段 + 关卡确认

超过半天的任务，不要一口气委派。拆成阶段，每个阶段一个可验收的交付物：

阶段1: 只做调研，输出方案文档(.omc/plans/xxx.md)，不要改任何代码
阶段2: 按方案实现核心链路，跑通最小闭环
阶段3: 补全边角 + 自测 + 让 code-reviewer 审查

每个阶段结束你验收一次，方向对了再继续。方向错误是最大的浪费，关卡确认是买保险。

3.3 让 AI 主动暴露不确定性

好的指挥者会强制 AI"先想后做"。几个有效的指令模式：

  • "先陈述你的假设，有不确定的先问，不要猜"；
  • "如果有多种实现方式，列出来给我选，不要默默挑一个"；
  • "如果有更简单的做法，直接说服我"；
  • "修 bug 前先追踪完整调用链，别套用第一个看起来合理的修法"。

这些模式值得写进项目的 CLAUDE.md/行为准则里，让它们成为默认行为而不是每次口头要求。本书附录里的行为准则模板可以直接抄。

3.4 反模式清单

反模式后果替代
"帮我做个 XXX"(无上下文无验收)AI 猜需求，大方向跑偏四要素齐全，或先用计划模式对齐方案
一次委派三天的工作量上下文爆掉，后半程质量崩拆阶段，关卡确认
AI 说"完成了"就信半成品、带病上线要求给出验证证据(测试输出/构建日志)
贴几千行日志进对话上下文被垃圾淹没给文件路径让它自己查，或先摘要
发现方向错了还让它继续错上加错，返工翻倍立刻 Esc 打断，纠正或回退重来

3.5 一个心态：你负责"对"，AI 负责"快"

AI 的生成速度是你的几百倍，所以方向性错误的成本主要由你承担。别吝啬前期的两分钟对齐：先看它的计划、先确认假设，比事后返工便宜十倍。反过来，方向确认之后就不要步步紧盯着——委派出去，等验收结果。

第 4 章 记忆体系：让 AI 记住你和你的项目

回忆第 1 章的心智模型："每天失忆的聪明同事"。治愈失忆的办法不是反复口头解释，而是建立一套分层的、AI 会自动读取的记忆体系。本章按"离 AI 由远到近"介绍各层。

4.1 五层记忆，各司其职

层载体放什么谁维护
全局个人层~/.claude/CLAUDE.md你的通用偏好、工作习惯你
项目共享层项目/CLAUDE.md、AGENTS.md项目架构、规范、领域知识、踩坑规则团队(随代码入库)
自动记忆层auto-memory(~/.claude/projects/<proj>/memory/)会话中发现的关键事实、纠偏、项目状态AI 在对话中自动读写
项目运维层OMC: notepad / project-memory / state优先上下文、工作笔记、编排状态AI + 你
知识库层OMC: wiki(.omc/wiki/*.md)架构决策、调试案例、约定、经验文章AI + 你

4.2 CLAUDE.md 怎么写才有效

CLAUDE.md 是杠杆率最高的一层记忆。写得好，AI 的输出质量上一个台阶；写得差(或者堆满 AI 生成的水话)，反而稀释重点。几条原则：

  • 写"AI 猜不到的东西"：构建命令、目录结构、特殊约定、易错点。"请写出高质量代码"这类话毫无价值；
  • 写"规则"而不是"描述"："控制器由框架缓存，不要在 Awake() 里手动缓存" 比 "控制器会被缓存" 有效得多；
  • 写"为什么"：踩坑规则要带上后果，比如"漏传 _L() 的格式参数会导致运行时报错"；
  • 控制长度：它每次对话都会被读入，只放高频使用的核心内容；低频知识放 wiki，按需查。

4.3 auto-memory：会话中的自动沉淀

Claude Code 有一个每项目独立的自动记忆目录。当你在对话中说"记住：配置表只能改 Excel 再导出，不许直接动 Luban 产物"，AI 会把它写成一条结构化记忆，并在未来相关对话中自动调出。适合存：

  • 你的纠偏("以后这类问题先给我方案再动手")；
  • 跨会话的项目状态("X 功能分支进行中，下一步是 Y")；
  • 环境怪癖("这台机器 git 外网被拦，装东西走内网镜像")。

经验法则：口头说一遍就丢的信息不值得记；让你说过第二遍的信息值得写进记忆。

4.4 OMC 的项目运维层

OMC 在项目里维护一个 .omc/ 状态根，其中和记忆相关的有：

  • notepad：分区的工作笔记。优先上下文区(Priority)每次会话必读，适合放"当前最重要的事"；Working 区放临时状态(7 天自动过期)；Manual 区永不清理；
  • project memory：结构化的项目记忆(技术栈/构建/约定/架构笔记/常备指令)，适合放"常备指令"(比如"所有改动必须过 code-reviewer")；
  • state：各编排模式(autopilot/ralph/team...)的进行时状态，中断后可恢复。

4.5 知识库层：wiki

低频但重要的知识——架构决策、一次艰难的调试复盘、团队约定——放 CLAUDE.md 太占上下文，丢了又可惜。OMC 的 wiki skill 在 .omc/wiki/ 维护一组带分类、标签、交叉引用的 markdown 页面，AI 可以写入也可以检索。它的设计目标是跨会话复利：每次踩坑复盘写一页，一年后这个知识库就是团队的隐形资产。

4.6 AGENTS.md 与 deepinit

AGENTS.md 是给子智能体和第三方工具读的项目说明书。OMC 的 deepinit skill 可以扫描整个代码库，分层生成层级化的 AGENTS.md 文档树(根目录总览 + 各子目录的局部说明)，一次初始化，后续增量维护。新项目接手时先跑一次 deepinit，能显著降低 AI 的探索成本。

4.7 记忆的维护：会腐烂，要修剪

  • 发现某条记忆过时/错误，让 AI 当场更正或删除；
  • CLAUDE.md 超过几百行就该"降级"：高频留原地，低频移去 wiki；
  • 记忆冲突时，新信息覆盖旧信息，并记下"为什么改"。

第 5 章 OMC 入门：多智能体定义与路由

oh-my-claudecode(OMC)是一个 Claude Code 插件，把单个 AI 会话升级成一支"虚拟团队"。本章介绍它的角色分工与路由逻辑。

5.1 OMC 是什么

OMC 的核心思想：作者和审查者分离，规划和执行分离。主会话作为"指挥官"不亲自下场写代码，而是把工作路由给专职 Agent，每个 Agent 用适合其任务的模型档位运行：

角色Agent模型档位职责
规划planner / architectOpus把模糊需求变成可执行计划
执行executorSonnet按计划实现，复杂任务可上调
审查code-reviewer / criticOpus独立审查，不和作者混用上下文
验证verifier按规模选档用证据确认"真的做完了"

除此之外还有专家位：debugger(根因分析)、tracer(证据驱动的调用链追踪)、test-engineer、document-specialist(查外部文档)、designer、writer、git-master、explore 探索位，以及游戏项目里的"配置策划"子智能体(负责 Excel 配置表操作)。

5.2 模型路由：好钢用在刀刃上

OMC 的原则是"按任务难度配算力"：

  • haiku：查路径、改文案这类秒级任务；
  • sonnet：标准实现、常规改动；
  • opus：架构分析、深度审查、疑难调试；
  • fable：最难的问题。

对话里直接说"用 opus 深入分析"即可覆盖默认路由。

5.3 标准协作流程

一个完整的 OMC 委派长这样：

你: 用 plan 模式调研"聊天撤回"需求，输出计划
AI: 派 planner/architect 出方案 → 你确认方案,不是确认细节
你: 执行这个计划
AI: 派 executor 实现 → 派 code-reviewer 发现2处中等问题 → executor 修复
AI: 派 verifier 收集测试/构建证据 → 汇报
你: 验收 + 决定是否提交

关键设计：审查者不复用作者的上下文。executor 写完的代码，由一个没有"作者滤镜"的 code-reviewer 在独立上下文里重新读一遍。这解决了单体 AI"自己写自己夸"的问题。

5.4 什么时候不编排

编排有开销(多智能体各带一份上下文，更慢更贵)。简单任务直接让主会话干反而快。经验阈值：

  • 改动 ≤ 3 个文件、一次对话能完成 → 主会话直接干；
  • 多文件/重构/疑难 debug/需要独立审查 → 编排；
  • 整条链路你都不用盯 → 用第 7 章的自主模式。

5.5 安装与检查

/plugin install oh-my-claudecode      # 插件市场安装
/oh-my-claudecode:omc-setup           # 刷新安装与配置
/oh-my-claudecode:omc-doctor          # 诊断安装问题
/oh-my-claudecode:cancel              # 取消任何正在运行的 OMC 模式
DISABLE_OMC=1                         # 环境变量开关,一键停用

第 6 章 OMC 核心工作流：plan → execute → review → verify

这是 OMC 的"正字法"流程，也是日常 80% 的委派都应该走的路。四个阶段各由一个专职 Agent 负责，你只在关卡处确认。

6.1 全景图

需求
 │
 ▼
plan(规划)     planner/architect 出方案 → 你确认方向,不必逐行看
 │
 ▼
execute(执行)  executor 按计划实现,每步带验证点
 │
 ▼
review(审查)   code-reviewer 独立上下文审查,按严重度分级报告
 │
 ▼
verify(验证)   verifier 收集证据:测试/构建/复现,确认"真的做完了"
 │
 ▼
你验收 → 提交

记住一条主线:每个阶段的产出就是下一阶段的输入。计划文档喂给 executor,实现结果喂给 reviewer,review 后的最终态喂给 verifier。

6.2 plan:先对齐方向,再谈实现

调用 /oh-my-claudecode:plan(或对话里说"用 OMC plan 流程")。规划 Agent 会:

  • 探索代码库、读 CLAUDE.md/AGENTS.md、必要时问澄清问题(OMC 还有 deep-interview/ralplan 两个专门的深度澄清入口,适合需求非常模糊时);
  • 产出一份计划文档(通常落在 .omc/plans/);
  • 你重点审:目标对不对、边界清不清、有没有漏掉关键约束、验证方式是否可信。

关卡原则:确认方案,不确认细节。方向和边界你把关;类怎么拆、函数叫什么名字,放手让 AI 定。

红线:计划未确认前不许写代码。在指令里明确"先出计划,等我确认再动手"。

6.3 execute:带验证点的执行

调用 /oh-my-claudecode:execute。executor 拿着已确认的计划分步实现,要点:

  • 复杂实现显式说"executor 用 opus";
  • 要求每步给出验证证据,不要"看起来写完了"就进下一阶段;
  • 执行中发现计划有误,让它停下来报告,而不是擅自改方向。

6.4 review:独立上下文的作者-审查者分离

调用 /oh-my-claudecode:review(OMC 的审查技能)。code-reviewer 在一个全新的上下文里重新读改动:

  • 按严重度分级(critical/major/minor)给出结构化报告;
  • 审查范围三选一:工作区 diff、指定分支/PR、最近提交;
  • 报告直接给到文件:行号,便于 executor 修复;
  • 审查报告也喂给 executor 修复,修完再审,直到无 critical/major。

6.5 verify:用证据说话

调用 /oh-my-claudecode:verify。verifier 的工作是回答一个问题:"你怎么知道它真的能跑?"

  • 小改动:跑一遍 luacheck/单元测试即可;
  • 标准:构建 + 测试 + 关键路径手工复现;
  • 安全相关:让 security-reviewer 单独过一遍。

验收时要求 AI 汇报"验证证据"(命令与输出摘要),而不是"我觉得完成了"。这是防止"AI 自称完成"的第一道防线。

6.6 把流程变成肌肉记忆

日常使用不需要记命令——把这套流程写进 CLAUDE.md 的协作约定里,例如:

## 协作约定
- 非琐碎改动先 plan 后 execute
- review 必须走独立上下文的 code-reviewer,不允许自查自审
- 完成前必须 verify,汇报验证证据
- 提交信息格式: 类型: 描述

写进文件的记忆 > 对话里的口头要求。

第 7 章 自主模式：autopilot / ralph / ultragoal / team

编排流程里你还要在关卡确认方案、验收结果。自主模式更进一步：你只给定目标，AI 自己规划、执行、验证、循环，直到完成或被你叫停。适合"你不用中途盯"的任务：大重构、批量迁移、长测试循环。

7.1 autopilot：全自动驾驶

说 "autopilot" 或调用 /oh-my-claudecode:autopilot，给一句话目标：

autopilot: 把 LuaScripts 里所有 TODO 注释清理干净，
每处要么实现要么升级为明确 issue 提示，保持 luacheck 通过

它自动走 plan → execute → review → verify 全链路，无需关卡确认。适合边界清晰、验收可自动化的任务。若验收不可自动化，不要用 autopilot。

7.2 ralph：循环直到完成

ralph 技能实现"循环直到完成"：给一个任务，它反复迭代（规划→执行→验证→自我修正），可配置一个审查者 Agent 做完成判定。适合有明确终点的长循环，比如"迁移完这 50 个文件"。

7.3 ultragoal：持久多目标台账

ultragoal 把目标写成持久化的计划/台账文件（.omc/ultragoal/），跨会话追踪多个目标的进度，适合长周期项目。

7.4 team：多 Agent 协同

/oh-my-claudecode:team 显式启动 N 个 Agent 协同处理共享任务列表。适合大任务需要并行分工（比如同时调研 3 个模块）。

7.5 怎么选模式

场景推荐原因
边界清晰、验收可自动化autopilot全链路无人值守
明确终点的长循环（迁移/批量）ralph循环直到完成判定通过
长周期多目标ultragoal持久台账跨会话追踪
大任务并行分工team共享任务列表
需求模糊plan / deep-interview / ralplan先澄清再执行
研究型问题research有出处的调研报告

所有模式可随时 /oh-my-claudecode:cancel 取消并清理状态。

7.6 自主模式的护栏

  • 只在验收可自动化时用：自主模式最大的风险是"在错误的路上跑很远"，护栏是机器可判定的验收标准；
  • 给足上下文再放行：启动前写清约束（"不要动 DataAccess 生成代码"、"不要 push"），自主模式下你说不上一句话；
  • 用 git 兜底：放行前工作区干净、分支正确，出问题可整体回滚；
  • 设上限：例如"最多迭代 10 轮，超了停下汇报"。

第 8 章 知识沉淀：wiki / remember / deepinit / skillify

第 4 章讲了"记忆"——记住事实和纠偏。本章讲更进一步的事：把经验变成可复用资产，这是"AI 进化"的核心机制。

8.1 从经验到资产：三级火箭

一次好经验
  →(wiki)     知识页,可检索,跨会话复用
  →(skillify) 技能草稿,固化成可调用技能
  →(skill)    正式技能,斜杠命令触发,团队共享

8.2 wiki：团队知识库

"LLM Wiki"的核心论点：让 AI 自己维护一个 markdown 知识库，把每个值得记住的东西写成页面，带分类、标签、交叉引用，让知识产生复利。OMC 的 wiki skill 实现了这一点：

  • /oh-my-claudecode:wiki 写入/更新页面（合并策略是追加，从不静默覆盖）；
  • 工作过程中 AI 可以自动沉淀（调试复盘写成 debugging 类页面）；
  • 检索时 AI 按关键词/标签查询，把结论带回对话。

8.3 remember：决定什么值得记、记在哪层

/oh-my-claudecode:remember 不是"什么都存"的仓库，而是一次知识分类决策：会话里出现一条值得保留的知识，先判断它属于哪一层。

层放什么
CLAUDE.md / AGENTS.md每次对话都要生效的规则
project memory / notepad项目运行时状态、常备指令
wiki低频但重要的知识、复盘文章
skill重复流程的自动化封装

分类错层会浪费：规则进 wiki 会被忽略，知识进 CLAUDE.md 会稀释上下文。选层就是设计。

8.4 skillify：把会话里的好流程固化成技能

skillify 把会话中摸索出的好流程起草成技能草稿（触发词、步骤、验证方式），你审阅后正式启用。此后一个斜杠命令即可重放整个流程。

这正是"AI 进化"最直接的形式：AI 把自己摸索出的流程沉淀成自己的技能。

8.5 deepinit：给新项目做"入职体检"

OMC 的 deepinit 生成带增量维护的分层 AGENTS.md 文档树。新接手项目或冷启动时跑一次，后续结构变化时增量更新，子智能体的探索成本显著下降。

8.6 沉淀的时机判断

不是所有东西都值得沉淀。三个判断标准：

  • 第二遍：同一件事你解释了第二遍 → 值得记；
  • 30 分钟：排障超过 30 分钟 → 值得写一页 wiki 复盘；
  • 第三遍：同一流程手工走了第三遍 → skillify 技能化。

口诀："第二遍记忆、30 分钟复盘、第三遍技能化"。用这套标准，知识库不会变成垃圾场。

第 9 章 持续进化的闭环

前面章节的零件都齐了。本章把它们组装成一个可运转的"进化系统"：反馈 → 记忆 → 技能 → 工作流固化。

9.1 进化闭环的四个环节

把指挥、记忆、编排、沉淀四个机制连成一个环：

干活(委派/编排/自主模式)
  ↓
反馈(验收中发现问题,或说"不对,应该……")
  ↓
沉淀(第二遍记忆 / 30分钟复盘进 wiki / 第三遍 skillify)
  ↓
下一轮自动生效(记忆自动读取,技能直接调用)
  ↓
干活 ……

判断你的体系是否在进化，看两个信号：

  1. 重复解释变少：同一个纠偏你说第二遍时，AI 应该已经记住了；
  2. 流程重放：以前手工走的流程，现在一句话重放。

9.2 三种时间尺度的"学习"

时间尺度机制动作
会话内上下文 + 纠偏Esc 打断、双击 Esc 回退、当场纠正
会话间五层记忆体系(第 4 章)说"记住:……"或跑 remember 分类决策
长期skillify / wiki / CLAUDE.md 修订把流程固化,把规则修订进文件

9.3 进化日志模板

建议每次"值得记的反馈"都追加一条日志(可放 wiki 的 session-log 类别)：

## 2026-10-11  背包断线重连 bug
- 现象: 重连后物品数量显示错误
- 根因: 配置读取没走缓存层
- 纠偏: "修 bug 先追踪完整调用链再修" —— 已写入 CLAUDE.md
- 沉淀: wiki/debugging-backpack-reconnect.md

三个信号说明你没有在进化：

  • 同一个纠偏说第三遍还不生效 → 记忆层选错了，检查该进 CLAUDE.md 的规则是不是进了 wiki；
  • AI 反复犯同类错 → 缺少机器可判定的验收标准；
  • 流程依赖你全程盯守 → 该 skillify 或上自主模式。

9.4 团队层面的进化

个人进化靠记忆，团队进化靠随代码入库的共享文件：项目 CLAUDE.md/AGENTS.md、wiki、技能都在仓库里，新人(和他们的 AI)第一天就继承全部经验。团队约定示例：

  • 踩坑必须写 wiki 调试复盘页；
  • 重复流程一律 skillify 固化；
  • CLAUDE.md 修订走 PR 评审，像代码一样对待。

第 10 章 实战：从需求到交付的完整演练

用一个贴近本书写作环境的例子串起全书：给一个 Unity 手游客户端加"聊天撤回"功能。例子中的技术点来自真实项目的 CLAUDE.md 约定。

10.1 需求 → 委派指令

产品说"加个消息撤回"。直接转述给 AI 是反模式。先按四要素翻译成委派指令：

功能: 聊天系统加"撤回消息",发出后 2 分钟内可撤回。
约束:
- 遵守项目 CLAUDE.md 的 MVVM 三件套(InitVM/InitBinds/InitEvents)
- 不改 UI 布局文件,只改 Lua 逻辑层
验收:
- 发消息→撤回→对方不再显示,本地服务自测通过
- luacheck 无新增告警
执行方式:
- 非琐碎改动: 先 plan 后 execute
- review 走独立上下文的 code-reviewer

注意两点：约束里直接引用 CLAUDE.md 的已有约定(不用重新解释)；验收里写明复现路径。

10.2 plan 阶段

切换计划模式(或 /oh-my-claudecode:plan)。AI 探索代码库后给出方案：

  • 聊天 UI 在 UI/Chat/UIChatMain.lua,消息数据在 _G.Root.Chat,撤回需要客户端标记 + 服务器广播；
  • 方案：协议加撤回请求/广播 → Mediator 处理 → VM 标记消息状态 → UI 订阅变化刷新列表。

你审方案的三件事：目标对不对、边界清不清、验证方式是否可信。确认后进入执行。

10.3 execute 阶段

/oh-my-claudecode:execute。executor 按计划实现：

  1. 协议层：撤回请求 + 广播消息定义；
  2. Mediator：_G.MediatorChat:RecallMessage(msgId)，更新 _G.Root.Chat；
  3. UI 层：UIChatMain 订阅消息变更，撤回的条目渲染为提示文案。

每步要求验证证据。执行中发现协议字段和服务器对不上，AI 停下来报告而不是硬编——这正是 3.3 节"先想后做"约定的作用。

A.2 减少打扰:提升自动化,少跟 AI 来回确认

很多文章提到 claude --auto —— 这个指令并不存在,准确写法是 claude --permission-mode auto。下面按"放权程度"从轻到重排列:越往下越自动、打扰越少,也越需要你信任运行环境。

# 1. 权限模式(放权程度从轻到重)
claude --permission-mode manual             # 手动:每个新操作都询问(默认)
claude --permission-mode acceptEdits        # 自动接受文件编辑 + mkdir/mv/cp 等
claude --permission-mode auto               # 自动模式:低风险操作直接放行,
                                            #   危险命令/联网等风险操作由后台分类器
                                            #   审核是否与你的请求一致
claude --permission-mode bypassPermissions  # 跳过全部权限检查

# 2. 一路狂奔(危险,只建议在容器/虚拟机等隔离环境使用)
claude --dangerously-skip-permissions

# 3. 会话内随时切换,不用重启
Shift+Tab                              # 循环切换 手动 → 自动编辑 → 计划 模式
/permissions                           # 可视化管理 allow / ask / deny 规则
权限弹窗选 "Yes, and don't ask again"   # 该命令永久放行,写入 .claude/settings.local.json

# 4. 白名单:精确放行高频命令(日常推荐)
# 项目 .claude/settings.json 里配置:
#   { "permissions": {
#       "allow": ["Bash(npm run *)", "Bash(git commit *)"],
#       "deny":  ["Bash(git push *)"] } }
# 临时放行: claude --allowedTools "Bash(npm run *)"

# 5. 无人值守:脚本 / CI 里跑
claude -p "跑通测试并修复失败项" --permission-mode acceptEdits
claude -c                              # 继续最近一次会话,不用重新交代背景

推荐组合:日常用 auto 模式起步,配合白名单放行高频命令,把推送/删除类操作留在 deny 名单;工作区干净、有测试兜底时再逐步放权;只有容器或一次性虚拟机里才用 --dangerously-skip-permissions。放权越多,AI 打扰越少,但出错时的破坏半径也越大——自动化程度应该跟着你的回滚能力走。OMC 侧的无人值守编排(autopilot / ralph / ultragoal,见第 7 章)与权限模式正交:权限决定"敢让它干什么",编排模式决定"它自己走多远"。
